# Web notifications: stored rows + Web Push delivery

## Goal

- Users get notifications generated by **any task or page** (Huey tasks and
  views alike) with one server-side call.
- Delivered **by web only**: bell + list page in the app, plus **Web Push**
  toasts that arrive even with the tab closed ("news-site" behavior).
- Rows live in a table **until explicitly deleted** — no TTL, no auto-purge,
  no expiry job. Deletion is the only lifecycle end.
- Framework feature: every app (ourapp, the gate's testapp overlay,
  docs/reference) inherits it; the bell lives once in the shared Layout.

## Decisions (settled with operator, 2026-09-17)

- **Placement: djangoapp** (framework), like UserHistory/UserSessionIndex —
  not ourapp. App code only calls the record helper.
- **Read state: yes** — ``read_at`` column (null = unread) drives the badge;
  read is presentation state, not lifecycle. Rows still only removed by
  DELETE.
- **Delivery: full Web Push now** (service worker + VAPID + pywebpush), not
  SSE/polling-first. Open-tab bell freshness rides the service worker's
  postMessage + a slow visibility-paused fallback poll — no SSE endpoint.
- Notification model follows the **UserHistory pattern**: plain
  ``models.Model`` + uuid7 ``public_id``, NOT ``BaseModel`` (save_with_logs
  would double every system-generated write with an audit-log row).

## Design

### Models (``djangoapp/models/notifications.py``)

```
Notification:
    public_id  CharField(36), unique, default=generate_uuid7_id
    recipient  FK → User, on_delete=CASCADE
    kind       CharField(50)      # "task.done" etc — icon/filter bucket
    body       TextField
    url        CharField(blank=True, default="")   # optional deep link
    read_at    DateTimeField(null=True, blank=True)
    created_at DateTimeField(auto_now_add=True)
    Meta: index (recipient, -created_at)

PushSubscription:
    user       FK → User, on_delete=CASCADE
    endpoint   URLField(unique=True)   # the push service's URL per browser
    p256dh     CharField               # client encryption keys
    auth       CharField
    created_at DateTimeField(auto_now_add=True)
    Meta: index (user,)
```

- CASCADE on recipient: notifications and subscriptions die with the user.
- ``Notification.record(recipient, kind, body, url="")`` classmethod (the
  ``UserHistory.record_*`` pattern): one call shape usable from Huey
  workers (no request) and views alike. Returns the row.

### Dispatch (server → push service)

- Inside ``record()``: create the row, then
  ``transaction.on_commit(lambda: _push(notification))``.
- ``_push``: for each of the recipient's PushSubscriptions,
  ``pywebpush.webpush(subscription_info, json_payload, vapid_claims, ttl=…)``
  with payload ``{kind, body, url, created_at}``.
  - **404/410 → delete the subscription** (self-pruning dead endpoints).
  - Any other failure: structured-log and continue — a failed push must
    never propagate into the task/view that recorded.
  - Delivery is ASYNC: on_commit enqueues the ``deliver_push`` Huey task
    (djangoapp/tasks.py) whose ``notify_sessions`` runs the fan-out — no
    request path ever waits on push-service HTTP (shipped in 40a376c).
- New dependency: ``pywebpush`` (uv).

### VAPID keys (env)

- ``VAPID_PRIVATE_KEY`` / ``VAPID_PUBLIC_KEY`` / ``VAPID_SUBJECT``
  (a ``mailto:``) in the credentials env: ``.env.example`` +
  ``.env.vm.example`` sentinels; ``./testvm`` generates the pair at
  provisioning like the other secrets (one-liner via pywebpush's key
  helper or ``npx web-push generate-vapid-keys``).
- The public key reaches the browser via Inertia shared props (it is
  public by design — only the private half is secret).

### Endpoints (existing mount pattern; ``make_ninja_api``-style CSRF on,
every query scoped to ``request.user`` — a user only ever sees and act on
their own rows; address rows by ``public_id`` only, never pk)

- ``GET  /notifications`` — Inertia page (component ``Notifications``):
  list newest-first, mark-read, delete, clear-all.
- ``POST /notifications/api/subscriptions`` — save the browser's
  subscription (create-or-update by endpoint).
- ``DELETE /notifications/api/subscriptions`` — best-effort unsubscribe
  (also fired on logout so a shared browser stops receiving the previous
  user's notifications).
- ``POST /notifications/api/<public_id>/read`` · ``…/read-all``
- ``DELETE /notifications/api/<public_id>`` · ``POST …/clear``
- Unread count in shared props (``SharedPropsMiddleware``) for first
  paint; count query is the ``(recipient, read_at IS NULL)`` filter, served
  well enough by the ``(recipient, -created_at)`` index (a read_at-partial
  index was consciously forgone — see the model Meta comment).

### Frontend

- **Service worker** (``frontend/src/web-push-sw.js``, served from the
  bundle root): ``push`` → ``showNotification(body)`` carrying the deep
  link; ``notificationclick`` → focus an existing client / open the URL;
  then ``clients.matchAll()`` + ``postMessage`` so open tabs update the
  bell count live.
- **Bell in ``Layout.vue``** navbar (next to "Hello, …"): unread badge,
  links to ``/notifications``; 60s visibility-paused fallback poll for
  the count (push covers liveness; the poll only heals drift after
  sleeps/reconnects).
- **"Enable notifications" button** on the page (explicit gesture, never
  auto-prompt): ``Notification.requestPermission()`` →
  ``pushManager.subscribe(applicationServerKey=VAPID_PUBLIC_KEY)`` → POST
  the subscription.
- Logout: best-effort DELETE subscription before the form submits.
- ``HumanizedTime.vue`` for "2 min ago" timestamps.

## As-built deviations (2026-09-17)

- **One VAPID secret, not two**: pywebpush 2.5.0 dropped the
  ``vapid_public_key`` parameter (it derives the public half from the
  private key), and a PEM value would span lines (systemd EnvironmentFile
  can't). Env carries ONLY ``VAPID_PRIVATE_KEY`` (single-token
  base64url); the public key is derived at CALL TIME by
  ``djangoapp.models.notifications.vapid_public_key()`` — a mismatched
  pair is now impossible. Generated by ``manage.py generatevapid``
  (``--check`` reports what the current env derives to).
- **No VAPID_SUBJECT knob** (post-review follow-up): the RFC 8292
  contact is DERIVED at send time — ``vapid_subject()``
  (djangoapp.models.notifications) returns ``mailto:`` of the first
  superuser with an email (lowest pk, email-less ones skipped),
  ``lru_cache``-memoized for the process life (tests
  ``cache_clear()``). No superuser email → delivery skips (warning),
  rows still store. The env examples and settings carry no subject.
- **Bell count via shared props, not a poll/endpoint**: the unread count
  is an Inertia shared prop (``SharedPropsMiddleware``), refreshed between
  visits by partial reloads (``router.reload({only})``) on the SW's
  postMessage, the page's actions, and a ``visibilitychange`` → visible
  nudge (the one path that covers push-less browsers parked on a page).
  Cost: +1 COUNT query per authenticated request (API/XHR included —
  shared props are computed before the response shape is known) → frozen
  query budgets in ``djangoapp/tests/views/test_users.py`` re-baselined;
  exact-props home tests (ourapp + docs/reference — the reference copy was
  ALREADY stale, missing ``login_providers``) updated.
- **uv exclude-newer is a soak period, not a freshness floor**: the repo's
  ``exclude-newer = "P7D"`` excludes releases YOUNGER than 7 days; older
  releases pass freely, so pywebpush (2.5.0, weeks old) resolves under the
  bare global filter. An initial per-package ``exclude-newer-package`` block
  was added on a misreading of the semantics and later removed — fresh
  resolution with the bare filter locks pywebpush 2.5.0 + http-ece 1.2.1
  identically (verified 2026-09-17 with a scratch probe project).
- **Route order matters**: ninja matches per-operation URL patterns in
  registration order — the literal ``/api/subscriptions``, ``/api/clear``,
  ``/api/read-all`` routes register BEFORE the ``/api/{public_id}``
  wildcards, which would otherwise shadow them (405).
- SW lives in ``frontend/public/web-push-sw.js`` (Vite copies verbatim →
  ``/static/djangoapp/web-push-sw.js``); scope-limited to /static/, it
  DELIBERATELY controls no pages — its ``clients.matchAll`` calls pass
  ``includeUncontrolled: true`` (controlled-only would always be empty)
  and window matching keys on the app origin. Firefox+playwright
  ``page.reload()`` hangs with a registered SW — the e2e re-visits
  instead.

## Post-review fixes (2026-09-17, three-agent review)

- SW scope blocker: ``includeUncontrolled: true`` + origin-based window
  matching (above) — live bell refresh and focus-on-click now actually
  fire; postMessage wrapped into the same ``waitUntil`` as display.
- Enable/disable state keys on ``pushManager.getSubscription()``, not
  ``Notification.permission`` (permission stays "granted" after Disable);
  both buttons re-sync from the browser after failures.
- ``webpush()`` gets ``timeout=10`` — the default (None) could block the
  ``record()`` caller forever on a hung push-service connection.
- ``_push`` containment widened: the subscription fetch/iteration and
  endpoint pruning also sit inside the never-propagate guard.
- Logs carry the endpoint HOST only (capability URL, RFC 8030) — matching
  ``PushSubscription.__str__``.
- ``vapid_public_key()`` degrades to "" (push off, warning logged) on a
  malformed key instead of 500ing the page.
- Untrusted SW navigate URLs constrained to same-origin paths in the
  bell; unrelated SW messages ignored; subscribe response now validated
  (``SubscribeResponseSchema``); VAPID key rotation drops and resubscribes
  a stale subscription; PushSubscription's redundant FK index dropped
  (Django auto-indexes user_id); Notification ordering tiebreaks on pk.
- ``test_subscribe_requires_vapid`` forces VAPID off explicitly (env
  keys would otherwise flip it); ``test_record_pushes_only_after_commit``
  now asserts the callback is captured-but-deferred (it could never fail
  before).

## Session-bound subscriptions (2026-09-18, third iteration)

Logout unsubscribe went through three designs: client-side keepalive
DELETE (racy), a ``user_logged_out`` signal deleting by session_key
string (worked, but stringly + signal-timed), and finally the shipped
one — ``PushSubscription.session_index`` is a OneToOne to
``UserSessionIndex``, riding the existing CASCADE chain:
Session → index → subscription. Any session death (logout flush,
logout-all, ``clearsessions`` GC — now a daily Huey crontab in
ourapp/tasks.py) drops exactly that browser's subscription,
referentially. Subscribe get_or_creates the index row (the middleware
backfills lazily; a first-request subscribe can beat it).

Delivery API collapsed to ``notify_sessions(user, payload) -> int``
(the one delivery core, called by the ``deliver_push`` Huey task):
``Notification.record`` = store + on-commit enqueue. ``_deliver`` is the
private transport. (The rowless ``push_test`` probe was later REMOVED —
6ab1955 — the page's Send-test button now records a real notification
through the same pipeline, no special case.)

A one-shot ``just_logged_in`` session flag (set by the login signal,
popped by SharedPropsMiddleware into the landing render) drives the
bell's silent rebind: re-POST the still-held subscription after
re-login, recreating the row logout cascaded away.

Cost note: each session flush/delete now costs one extra collector
SELECT (the deeper CASCADE probe) — users-suite budgets re-frozen +1.

## Risks / notes

- Push payloads are encrypted to the subscription's keys — keep payloads
  small (the body, not the world); the DB row remains the source of truth.
- pywebpush is unmaintained-ish (Mozilla archive status) — acceptable:
  it implements RFC 8291/8292 over ``cryptography``; swap-in later is
  confined to ``_push``.
- One subscription per browser-user pair; two users sharing a browser
  re-subscribe per login (logout unsubscribe keeps delivery private).
- iOS Safari requires the site be installed to the home screen for push —
  known platform limit, not a design gap.
- VM deploy runs three migrations: 0023 (the two tables), 0024
  (pre-existing drift — the ``logout_all`` UserHistory action choice never
  had its migration; makemigrations emitted it during this feature), 0025
  (``session_index`` O2O; hand-written AddField is safe only because no
  populated pushsubscription table exists anywhere yet).
