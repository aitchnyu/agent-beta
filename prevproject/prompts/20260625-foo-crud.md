# Foo CRUD: class-based views on a concrete FooModel

A simpler, class-based CRUD system (`FooView` over `FooModel`) that mirrors the
existing `BaseView`/`BaseModel` machinery but replaces `include_columns` with a
declarative, behavior-carrying `columns` dict on the view. Built step by step,
reusing the per-field serialization/validation/public-id machinery from
`_BaseModelMixin` and `BaseView` wherever possible.

## Goal

A view like:

```python
class ABCStuffView(FooView):
    model = ABCStuffModel            # a FooModel child
    columns = {
        "char_field": Charfield(editable="createonly"),
        "char_choice_field": CharChoicefield(),
        "text_field": Textfield(),
        "integer_field": Integerfield(),
        "boolean_field": Booleanfield(),
        "decimal_field": Decimalfield(),
        "datetime_field": Datetimefield(),
        "file_field": Filefield(editable="createonly"),
        # "ref_field": Reffield(),   # FK — deferred
    }
```

Endpoints (all Inertia pages, POSTs via ninja):
- `GET /create`, `POST /create`
- `GET /update/<public_id>`, `POST /update/<public_id>`
- `GET /` — list: links to each row, **no pagination/table**
- `GET /id/<public_id>` — details
- `GET /id/<public_id>/download/<colname>` — file download

## Confirmed decisions

1. **Model/view stay separated** (like `BaseView`/`BaseModel`). `columns`
   lives on the `FooView` subclass; the model is a `FooModel` child that
   defines the Django fields. The view is the source of truth for which
   columns are engaged and their editability — it bypasses the model's
   `include_columns`/`resolve_columns`.
2. **`FooModel` is concrete → multi-table inheritance.** Child models are
   multi-table inheritors (a child table + the `foomodel` parent table joined
   via `foomodel_ptr`). `public_id`, `created_at` live on the parent and are
   inherited.
3. **`createonly` → hidden from the update form** (still shown in details).
   `never` → display only. `always` (default) → editable on create and update.
4. **No audit trail.** `FooModel.save_stuff()` overrides to validate + `save()`
   only — no `RowUpdate`, no notifications. Delete/comments/filters are out of
   scope for now.
5. **New list page component** (`FooList.vue`) — links-only, no pagination.
6. **`Reffield`/FK deferred.**
7. **Minimise public-ID gaps.** Generate the sequence id only after validation
   passes: keep generation inside `save()` (on create), and run
   `validate_unique()` *before* `save()` in `save_stuff` so a uniqueness
   collision fails before a sequence number is consumed. Generate nowhere else.
   (Note: Postgres `nextval` is non-transactional, so a gap on a *post*-generate
   rollback is still possible but minimised.)

## `columns` design (the descriptors add behavior)

```python
class Column:
    editable: str = "always"                 # "createonly" | "never" | "always"

    def is_editable(self, op) -> bool:
        # create  -> editable in ("always", "createonly")
        # update  -> editable == "always"
        # never   -> False
        ...

    def for_field(self, django_field) -> None:
        # validate the column's Django field type matches this kind
        ...

    # schema/input/td resolution delegates to the existing dispatch dicts
    # (SCHEMA_SERIALIZERS / VALUE_WRAPPER_TYPES / FORM_DESERIALIZERS) — reuse
```

Kinds: `Charfield`, `CharChoicefield`, `Textfield`, `Integerfield`,
`Booleanfield`, `Decimalfield`, `Datetimefield`, `Filefield` (and `Reffield`
later). Each validates its Django field type and carries the `editable`
behavior; serialization is **not** reimplemented.

## Reuse (do not rewrite)

- `_BaseModelMixin`: `columns_schemas()`, `value_wrappers()`, `feed_values()`
  (driven by the per-field-type dispatch dicts), `get_by_public_id_or_404()`,
  public-id generate-on-create in `save()`.
- `BaseView`: create/update/details/download bodies and the Inertia
  `CreateRow`/`UpdateRow`/`RowDetails` page wiring. `FooView` feeds the
  editable-filtered column list into these.

## Security note

`feed_values()` only processes the columns handed to it, so a `createonly`/
`never` field posted on update is ignored by construction — no extra guard
needed beyond passing the correctly-filtered column list.

## Build order (step by step)

### Phase 1 — Model
- [ ] `FooModel(BaseModel)`, concrete: `created_at` (auto_now_add),
      `public_id` (CharField, unique), `public_id_field="public_id"`,
      `public_id_generator = generate_sequence_id("%Y-%m-%d-ID")`
- [ ] `FooModel.save_stuff()` override: `validate_unique()` then `save()` only
      (no RowUpdate/notifications)
- [ ] migration for `foomodel`

### Phase 2 — Columns module (`djangoapp/columns.py`)
- [ ] `Column` base (editable behavior + type validation)
- [ ] `Charfield`, `CharChoicefield`, `Textfield`, `Integerfield`,
      `Booleanfield`, `Decimalfield`, `Datetimefield`, `Filefield`
- [ ] `Reffield` placeholder (deferred/skips FK for now)

### Phase 3 — FooView
- [ ] column resolver: read `cls.columns` → ordered Django fields, apply
      `is_editable(op)` filter
- [ ] `GET /create`, `POST /create` (reuse `BaseView` create bodies)
- [ ] `GET /update/<id>`, `POST /update/<id>` (createonly/never hidden from form)
- [ ] `GET /id/<id>` details
- [ ] `GET /id/<id>/download/<colname>` (reuse `download_file`)
- [ ] `GET /` list → links-only props
- [ ] URL patterns + ninja POST endpoints (a `FooView`-specific pattern/router
      builder, distinct from `BaseView`'s `/create-row` / `/list/-...-`)
- [ ] mounting helper

### Phase 4 — Smoke test
- [ ] fail when a `FooView` is mounted/used without a `columns` dict
- [ ] each `columns` key maps to a real model field of the matching type

### Phase 5 — Example + backend tests
- [ ] `ABCStuffModel(FooModel)` + migration (the char/text/int/bool/decimal/
      datetime/file fields)
- [ ] `ABCStuffView(FooView)` with the `columns` above
- [ ] tests: create get/post, update get/post (createonly hidden on update),
      details, download, list (links only)

### Phase 6 — Frontend
- [ ] `FooList.vue` + props schema (links to `/id/<public_id>`, no pagination)
- [ ] wire to the list endpoint
